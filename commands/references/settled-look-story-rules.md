# Rules for a story whose look is settled and whose binding table is missing

`hooks/scripts/story-rules.sh` prints one part of this file to the orchestrator (the plan-chunks skill) before it plans, when a story that is not planned yet came from a mockup, an annotate run or a dial and its `## Visual Direction` has no binding table with a filled-in row. A story that has its table, and every story that already has chunks, prints nothing. Each part is printed without its heading, under the facts the script checked.

## orchestrator, mockup

The user approved this story's look in the mockup named above. The binding table is how planning proves every part of that look was carried over: with it, a part the plan leaves out fails the plan check; without it, nobody notices. You build the table with the user, because some of what it needs is known only to them.

- **Read the mockup's record first,** when the facts name one. It says which option the user accepted (a mockup file can hold several), which parts they signed off, and which parts belong to another story. Bind only the accepted option.
- **One row for each thing the accepted option settles,** under the header `| Part | Role/State | Token | Value/Source |`. A row is something the user would point at and name on the page: a region or a control (the panel, its title, the reading well, the work list, a toggle), or a state of one that the user gets to by doing something (hover, selected, open, empty, error). The pieces that make it up ride in its row, with their anchors listed in the same Value/Source cell: its dots, glyphs, ticks, dividers and scrollbars, the overlays drawn with `::before` or `::after`, and the type inside it. A variant that only adjusts one effect of a part (an edge fade that changes with scroll position, a reduced-motion version of an entrance) stays in that part's row, named in its Role/State, and an entrance or a reveal is named there and on the story's Motion line, never in a row of its own. The builder copies every value from the mockup at those anchors, so the table's job is to name each thing once, not to list every rule: one panel or screen comes to about a dozen rows, and several dozen means pieces have been split out. A panel that frames several parts is one row for its container, and each part inside it gets its own row. When several panels repeat the same parts with different content or states, each part is still one row, and its Value/Source lists the anchor in every panel. Part names the element in plain words. Role/State says what it is for and the state shown. Token is the project token the record says that element uses (its `## New Values` and solidify outcome name them), or `-` where the record names none. Value/Source is the element's anchor in the mockup: its `id` or `data-section`, or its class selector where it has neither, written as: mockup `#the-id`, mockup `[data-section="name"]` or mockup `.the-class`. The file can be very large and hold inlined images, so search it for anchors and read only the matching ranges.
- **Leave out what the record rules out.** An element the record says was not signed off, or gives to another story, gets no row. Neither does anything the record calls scaffolding for the mockup itself (labels, replay buttons, staging behind the design).
- **Ask the user about the elements the record leaves unclear,** in one question that lists them: does each belong to this story? Ask nothing else. When nobody is there to answer, leave those elements out and name them in your report.
- **Place the table under `## Visual Direction`.** Fill the empty table there when the story has one; otherwise add the heading directly above `## Acceptance`, or at the end of the story when that is missing too. Above the table write one line, unless the story already has it: `**Source mockup:** <mockup file>, option <letter or name> - the approved look; port its values, keyframes and easing unchanged.` Leave out the option when the file holds only one. Where the story already has a Source mockup line, leave it as it is.
- **When the facts say the header has no `mockup:` line, add one** naming the mockup's folder, because the planner's and the builder's mockup rules look for it.
- **Change nothing else.** Every other line of the story, the mockup and its record stay exactly as they are.
- **When you can find no element with an anchor in the accepted option,** write no table and say so in one line. The planner still plans from the mockup.
- **Show the user the table you wrote,** under one line saying the story had none and it was built from the mockup, with any element you left out and why. When the facts say the tokens question has no answer on record, add one line: the mockup's new values were never offered for the project's tokens, so they are built as written and reported as "no token".

## orchestrator, annotate

The user approved this story's look on a live page, in the annotate run named above. The run's sheet, named above, holds every change they saw, one block per pin.

- **Build the table from the sheet, as the look stood at the end of the run.** The sheet records every change in order, and a later block often overrules an earlier one on the same element. Group the blocks by the element they style, then write one row for each group. Blocks style the same element when their pins' selector, component or resolved rule in the record's `## Pin Data` point at the same thing. A block for a state (`:hover`, `:focus`, a media query) is its own group, because it does not overrule the resting look. Use the header `| Part | Role/State | Token | Value/Source |`. Part is the element, in plain words. Role/State is `default` or the state the block styles. Token is the project token whose value equals the rule's, or `-`. Value/Source gives the declarations still in force for that group once every block has applied, worked out property by property (a later block replaces only the properties it sets), and names the blocks they come from, as in: session.css `annotate-key 1728000000000`, `annotate-key 1728000000450` - `.toolbar .save { padding: 12px 20px; color: #1a1a1a }`. A value an earlier block set and a later block replaced is not written.
- **A block that swaps text through `content:` or draws a new piece stands in for content, not a look.** It gets no row. Add one line for it under `## Scope` (add the heading when the story has none) quoting the pin from the run's record and what was shown, so the planner still plans it.
- **Place the table under `## Visual Direction`,** filling the empty table there when the story has one; otherwise add the heading directly above `## Acceptance`, or at the end of the story.
- **When the facts say the header has no `annotate:` line, add one** naming the run's folder.
- **Change nothing else.** Every other line of the story and the run's record stay exactly as they are.
- **Show the user the table you wrote,** under one line saying the story had none and it was built from the annotate run, and name any block you moved to Scope.

## orchestrator, dial

The user settled part of this story's look on a dial, on the live page. The dial record named above keeps the position they chose and what they said, not the values behind it, so no table can be built from it.

- **Tell the user in one line** that part of this story's look came from a dial and the story has no table, so the only values planning has are the ones the story's own text states.
- **Write no value of your own.** A value worked out from the letter or from the record would be a guess presented as their choice.
